## ADR-001：React + FastAPI

- 日期：2026-07-29
- 状态：Accepted
- 背景：后台管理系统，需要快速交付管理 UI 与 REST API。
- 决策：前端 React+TS+Vite；后端 Python FastAPI。
- 原因：符合公司前后端工程规范与 scaffold-kit 能力。
- 后果：需维护清晰 REST 契约与联调流程。

## ADR-002：使用 MySQL 并复用既有表

- 日期：2026-07-29
- 状态：Accepted
- 背景：爬虫已写入 `currency` / `rate`，DDL 已给定且要求复用。
- 决策：数据库采用 MySQL；ORM 映射既有表，不迁移到 PostgreSQL。
- 后果：与部分公司示例项目（PostgreSQL）不同；连接串、迁移与类型映射按 MySQL 处理；`rate.data` 保持字符串语义。

## ADR-003：鉴权双轨（Session + API Key）

- 日期：2026-07-29
- 状态：Accepted
- 背景：管理端是浏览器后台；对外查询是系统间调用。
- 决策：管理端 Session Cookie + CSRF；对外 `/public/*` 使用 `X-API-Key`。
- 原因：浏览器场景适合 Cookie；服务调用适合静态 Key；二者隔离降低误用风险。
- 后果：需实现会话表与 api_keys 表；Key 只存哈希；文档与中间件需分区清晰。
- 扩展：未来可换 Casdoor，但业务资源不绑定外部 ID 细节。

## ADR-011：海关字典第一版范围（国家/洲 + 共用 Redis）

- 日期：2026-07-31
- 状态：Accepted（同日补充共用 Redis 默认假设）
- 背景：旧占位「货币名称 ↔ code」不正确。业务为原始值 → 标准值映射；与第三方共用 Redis；内容审核不在范围。
- 决策：
  - 单表映射 + 类型字段；**不**拆国家/洲物理表。类型初始预置 `country`/`continent`；类型管理见 `customs_dict_type`（已归档）。
  - 标准值单字段；管理员自由填写；**不做** ISO/码表/标准值列表校验（仅非空、长度、唯一性等技术约束）。
  - MySQL 为本系统映射权威；同步失败不回滚 MySQL，可重试。
  - Redis **按类型拆 key**（正式 Hash + 缺失 ZSET）；本系统有读写权；**第三方也会写正式 Hash**。
  - 默认同步为**增量** `HSET`/`HDEL`；**禁止**第一版整表覆盖（temp+RENAME），以免删除第三方 field；可选重放同步且保留 Redis 中未知 field。
  - 缺失由第三方写入 ZSET；本系统处理：正式同步**成功后**再 `ZREM`；可导出；标准字典导入已交付（与缺失导出同表头 upsert，导入不自动 ZREM）。
  - **无物理删除**；停用代替删除；**原始值创建后不可改**。
  - 搁置：处理历史、操作日志、整表覆盖全量、标准值强制列表。
- 后果：字典能力已归档至 `openspec/specs/customs-dict/spec.md`；若日后确认仅本系统写正式 Hash，可再增加整表覆盖全量而不必改表结构。
- 补丁（2026-08-03）：解冻类型管理——表 `customs_dict_type`；可新建/改名/启停；编码不可改；有映射行不可停用；写路径校验启用类型。

## ADR-007：对外查询返回空列表而非 404（无数据时）

- 日期：2026-07-29
- 状态：Accepted
- 决策：货币存在但无匹配汇率时返回 200 + `items: []`；货币 code 不存在才 404。
- 后果：调用方可用空列表表示「无数据」。

## ADR-008：本地开发使用 MySQL，自行建表

- 日期：2026-07-29
- 状态：Accepted
- 背景：本机无公司库；需要空库自建表以开发联调。项目要求简单、效率优先，并与既有 DDL 对齐。
- 决策：本地继续使用 **MySQL 8**（推荐 Docker 一键起）；空库先执行 `deploy/sql/schema.sql` / `docs/data-contract.md` 中的 `currency`/`rate` DDL，再跑 Alembic 创建管理表。不改用 PostgreSQL / SQLite。
- 原因：与公司存量表结构一致，避免方言差异；简单项目不值得双库适配。
- 后果：开发者需本机或 Docker 提供 MySQL；无公司数据时用管理端或种子脚本录入少量样例即可。

## ADR-009：对外汇率 API 只按 code 查询

- 日期：2026-07-29
- 状态：Accepted
- 背景：调用方可按货币名或 code 查询；海关字典未来可能承担「名称 ↔ code」映射，但需求未定。
- 决策：对外 `GET /public/rates` **只接受 `code`**，不接受 `name`。管理端列表可用 `q` 按 name/code 搜索。
- 原因：名称易重名/多语言/不规范；code 稳定。名称映射留给后续字典能力，避免现在猜需求。
- 后果：调用方若只有中文名，需先在管理端或未来字典服务解析出 code；本系统 MVP 不提供按名查汇率。

## ADR-010：货币 code 格式约束

- 日期：2026-07-29
- 状态：Accepted
- 背景：业务上货币 code 为字母码（如 `CNY`）或带下划线的变体（如 `MYR_IM`）；既有 `currency.code` 列为 `varchar(10)` 且无 CHECK 约束。
- 决策：不改 DDL；在后端创建/更新时校验非空 `code` MUST 匹配 `^[A-Z_]{1,10}$`（大小写不敏感，入库前规范化为大写）；非法返回 400 `Currency.InvalidCode`。空/`null` 仍允许（兼容历史空值）。前端表单做同规则提示。
- 原因：与实际数据字典一致（含 ISO 三字母码及业务后缀如 `_IM`/`_EX`）；改库成本高且与「复用既有表」冲突。
- 后果：管理端与后续对外查询均按字母/下划线码理解 `code`；数字或特殊字符会被拒绝。
