# 02 编码规范

## 基本要求

- 新代码统一使用 `TypeScript`
- 组件文件统一使用 `tsx`
- 工具函数、常量、类型定义优先小而清晰
- 保持单文件职责单一，避免一个文件同时承载页面、接口、状态、转换逻辑

## 命名规范

| 类别 | 规则 | 示例 |
|------|------|------|
| 路由 | `kebab-case` | `trade-list` |
| 文件夹 | `camelCase` | `tradeList` |
| React 组件 | `PascalCase` | `TradeList` |
| hooks | `useXxx` | `useTradeList` |
| 工具函数 | `camelCase` | `formatTradeAmount` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_PAGE_SIZE` |
| 样式文件 | `index.module.less` | `index.module.less` |
| 类型 | 语义化命名 | `TradeSearchFormValues` |

## 类型规范

- 禁止无必要的 `any`
- 公共接口入参与返回值必须标注类型
- 复杂对象优先定义独立类型，不在函数签名中内联大对象
- 区分 `FormValues`、`DTO`、`ViewModel`

### 约束案例

```tsx
// ✅ 正确：独立类型定义，语义清晰

// ❌ 错误：内联大对象、泛化命名
function fetchData(params: { a: string; b: any; c: any }): Promise<any> {
  // ...
}

// ❌ 错误：滥用 any
const handleSubmit = (values: any) => {
  const result: any = transform(values);
};
```

## React 编码要求

- 页面组件负责组装，不负责承载大量业务细节
- 复杂逻辑抽到 hooks
- 数据转换抽到 utils / adapters
- 不在 JSX 中写大段条件分支和复杂 map 逻辑

## 通用约束

### 基础约束

- 优先复用已有模式，不新增平行方案
- 优先在现有目录中扩展，不随意新建顶层目录
- 优先复用 `tendata-ui` 与 `tendata-biz-components 业务组件库`，避免项目内重复造轮子
- 优先复用 `tendata-utils` 中已有工具能力，避免重复实现格式化和通用处理逻辑

### 查询页约束

- 查询条件默认值集中定义
- 参数转换逻辑单独维护
- URL 同步与回填逻辑单独维护

### 表格约束

- 列定义单独文件
- 分页、排序、筛选状态有统一处理方式
- 单元格复杂展示优先封装 formatter 或 cell 组件

### 图表约束

- 数据转换与 option 配置分离
- 空态、加载态、错误态处理一致
- 不在页面里直接堆一整段 ECharts 配置

### 可读性约束

- 单文件过长时主动拆分（建议单文件不超过 300 行）
- 单函数逻辑过深时主动拆分（建议单函数不超过 50 行）
- 注释解释"为什么"，避免注释"代码正在做什么"

## 禁止项

- 禁止复制旧项目中的历史写法直接落地
- 禁止为图省事跳过类型定义
- 禁止把通用逻辑散落在多个页面重复实现
- 禁止手写深路径导入（除非有明确团队约定）
- 禁止项目内重复实现已有组件库 / 工具库的同语义能力
- 禁止未确认兼容性直接升级内部库主版本
